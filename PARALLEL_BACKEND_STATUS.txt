# Impact of Parallel Backends on Bayesian/Optuna Methods

**Current Status:**
**No, the `parallel_backend` setting currently DOES NOT affect computation speed for Bayesian or Optuna methods.**

**Reason:**
In the current `wfo.py` implementation:
1.  **Bayesian Method**: The code explicitly hardcodes `n_jobs = 1` (single-threaded).
2.  **Optuna Method**: The `study.optimize()` call uses the default behavior, which is also sequential (`n_jobs=1`).

The `parallel_backend` configuration option you select in the GUI is retrieved but **ignored** by the logic for these two methods.

**Context:**
Bayesian optimization (including TPE used by Optuna) is inherently sequential: it uses the result of the previous trial to intelligently choose the next parameters. While parallelization is possible (using strategies like "Constant Liar"), it is often less effective than for Grid Search. Given that the underlying `run_backtest` function is already highly optimized (vectorized), adding process-based parallelism (like Dask/Ray) often adds more overhead than speedup for these specific algorithms on standard datasets.
